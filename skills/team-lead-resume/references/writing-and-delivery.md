# 한국어 작성과 제출

## 문서의 역할

| 문서 | 중심 질문 | 기본 구성 |
| --- | --- | --- |
| 이력서 | 어떤 직무를 맡아 어떤 범위의 경험을 쌓았는가 | 직무 요약, 관련 근거, 회사별 기간·역할, 학력·자격 |
| 경력기술서 | 왜 중요한 문제였고 왜 그 방법을 택했으며 결과는 어떤 의미가 있는가 | 회사·프로젝트·기간·범위, 개인 책임, 판단 근거·행동, 산출물·결과 |
| 자기소개서 | 왜 이 역할을 원하는가, 어떤 기준으로 판단하는가 | 실제 경험, 선택 이유·배운 점, 지원 동기, 앞으로의 기여 |
| 별도 후보자 양식 | 제출처가 지정한 사실은 무엇인가 | 원래 항목·순서·동의·서명 요구를 확인하여 작성 |

지정 양식과 분량을 우선한다. 자유 양식에서는 관련 경험이 먼저 보이도록 배열하되 모든 이력서를 1쪽 또는 2쪽에 맞추지는 않는다. 직무 용어와 도구명은 실제로 사용한 맥락과 역할에 연결한다. 경험 없이 공고의 단어만 복사하거나 숨은 키워드를 삽입하지 않는다.

## 기존 한국어 지침과 연결

한국어를 작성하거나 편집할 때는 사용자가 지정한 `ContextualWisdomLab/korean-writing-skills`의 `korean-editing`을 먼저 읽고 적용한다. 문장 지침은 해당 저장소에서 관리하며 이 스킬에 복제하지 않는다. 이 스킬의 한국어 편집에 적용한 판본은 다음과 같다.

- [korean-editing](https://github.com/ContextualWisdomLab/korean-writing-skills/blob/70b3a9ced7a102c2bda73d0d8ea3b7dd33c152c2/skills/korean-editing/SKILL.md)
- [이력서·경력기술서 지침](https://github.com/ContextualWisdomLab/korean-writing-skills/blob/70b3a9ced7a102c2bda73d0d8ea3b7dd33c152c2/skills/korean-editing/references/resume-writing.md)

이 자료는 사용자가 지정한 작성 지침이다. 채용 효과를 입증하는 연구로 취급하지 않는다. 원격 자료를 읽을 수 없으면 이 스킬의 근거 보존 절차로 작성을 진행하되, 해당 판본을 직접 적용했다고 말하지 않는다.

구체적인 역할·행동·결과를 자연스럽게 잇는다. `탁월한 리더십`, `혁신적인 성과` 같은 평가어보다 실제 결정과 근거를 중심으로 쓴다. 모든 문장을 동사로 시작하거나 피동 표현을 일괄 삭제하지 않는다. 독자의 이해에 필요한 약어는 처음 쓸 때 풀어 설명하고, 정확한 기술명·직함·날짜·단위를 보존한다.

대표 경험을 읽고 **왜 중요한 문제였나, 왜 이 방법과 순서를 택했나, 그 결과가 왜 의미 있나**라는 의문에 답할 수 있는지 점검한다. 필요한 이유가 자료에 있으면 문장에 남긴다. 자료에 없으면 공개 자료에서 조사할 수 있는 직무 맥락과 지원자에게 물어야 할 당시 판단을 구분한다. 문단 전체에서 배경·선택·결과의 관계가 드러나도록 쓰되, 같은 설명을 문장마다 반복하지 않는다. 정량 결과가 없더라도 확인된 문제의 중요성과 선택 근거는 남긴다.

## 앞부분 설계

1. **전문성 요약**: 경력의 중심, 반복해 맡은 문제, 목표 직무와 연결되는 확인된 경험을 2~4문장 정도로 요약해 시작한다. 이는 기본적인 편집 제안이며 회사 양식이 있으면 그 양식을 따른다.
2. **대표 근거**: 공고의 직무 설명(JD)과 관련이 높은 경험 3~5개를 우선 고른다. 개수보다 필수 요건을 뒷받침하는 근거가 중요하다. 같은 프로젝트를 쪼개 성과 개수를 부풀리지 않는다.
3. **경력 본문**: 공식 회사·직책·기간과 실제 프로젝트 책임을 구분한다. 관련 초기 경력이 경력의 중심이나 필수 요건을 설명하면 남긴다.
4. **서류 간 정합성**: 요약에서는 핵심 경험을 고르고 본문에서는 그 근거를 설명한다. 자기소개서에서는 같은 경험에서 내린 판단과 동기를 풀어 쓰되, 수치·직책·기간은 다른 서류와 일치시킨다.

## 분량을 줄일 때

중복된 소개를 먼저 줄이고, 관련성이 낮은 세부 사항과 내부 관리 용어를 차례로 덜어 낸다. 본인의 행동, 핵심 판단에 필요한 선택 근거, 기간, 팀 결과와 개인 기여, 불확실성을 설명하는 조건은 남긴다. 글자 크기와 여백을 과도하게 줄이지 않는다. 상세 경력이 길면 제출처가 허용할 때 별도 파일로 나눈다.

`박사과정 수료`를 `박사`로, 기획·검수를 개발로, 프로젝트 참여를 조직 총괄로 줄이지 않는다. 지원자가 희망하는 다음 역할을 이미 수행한 성과처럼 쓰지 않는다.

## 양식·ATS·파일 검증

| 상황 | 실행 |
| --- | --- |
| 회사 지정 표·문항이 있음 | 표와 문항 순서를 유지하고 그 안에 맞춰 쓴다. ATS 일반론으로 서식을 무단 변경하지 않는다. |
| 자유 양식이며 지원 시스템의 정보 추출 방식을 알 수 없음 | 명확한 제목과 읽기 순서, 선택 가능한 텍스트를 우선한다. 어떤 형식도 모든 ATS에서 통한다고 단정하지 않는다. |
| DOCX/PDF 요청 | 해당 문서 스킬로 만들고 최종 편집본 전체를 렌더링한다. 글자가 잘리거나 표가 영역을 벗어나는지 확인한다. 목록·쪽 나눔·빈 페이지·글꼴 대체 여부도 점검한다. |
| 지원 시스템에서 추출 확인 가능 | 이름·연락처·경력 날짜·회사·제목·본문의 추출 순서와 누락을 대조한다. 시험한 시스템과 파일 판본을 기록한다. |
| 렌더링이나 시스템 확인이 불가능함 | 검증하지 못한 범위를 별도로 알린다. 파일을 만들었다는 이유로 검증까지 마쳤다고 말하지 않는다. |

링크·연락처·지원 직무명·제출일·문서 버전을 대조한다. 날짜는 사용자의 시간대를 따른다. 동의·서명·법적 확인을 대신 추정해 채우지 않는다. 실제 지원서 제출이나 채용담당자 전송은 사용자의 해당 요청이 있을 때만 수행한다.

## 결과물과 확인 사항

완성 문서에는 확인된 사실을 자연스럽게 쓴다. 확인하지 못한 수치는 빼고, 결과를 이해하는 데 필요한 파일럿의 범위·기간·추정 조건은 남긴다. 작업용 표, 공고 해설, 확인할 사항은 별도 노트에 둔다. 필수 항목이 비어 있으면 해당 위치와 필요한 자료를 별도로 알리고 제출 준비를 마쳤다고 말하지 않는다.

검토 결과는 중요한 수정 이유와 사실을 확인할 질문으로 간추린다. 저장소에는 일반 지침과 가상 경력으로 만든 예문만 넣고, 지원자의 문서는 요청한 저장 위치에서 별도로 관리한다.
