# 팀장급 이력서 작성과 검토

채용 공고의 책임을 지원자가 실제 맡았던 일과 연결하라. **사람·의사결정·사업 결과에 대한 실제 책임과 증거**를 확인하라. 확인된 성과는 구체적으로 쓰고, 불명확한 사실로 빈칸을 채우지 말라.

## 필요한 자료를 고르기

| 작업 | 읽을 파일 |
| --- | --- |
| 유사 팀장급 채용 조사·직무별 책임 비교 | [채용 사례와 출처](references/hiring-cases.md) |
| 신규·낯선 직무 조사, MECE 기능분류·경계, 복합 직무·직무 전환 | [직무별 참고표](references/role-families.md) |
| JD와 경력 대조·리딩 범위·성과·경력 연수 판단 | [증거를 정리하는 절차](references/evidence-workflow.md) |
| 한국어 초안·지정 양식·분량·DOCX/PDF 제출 | [작성과 제출](references/writing-and-delivery.md) |

이 스킬은 최종 책임 산출물에 따른 15개 기능을 사용한다. 한 책임에는 한 기능을 배정하고, 복합 직무는 독립 책임으로 나누어라. AX·데이터 같은 기술, 산업, 관리 수준은 별도 속성으로 기록하라. 기능분류의 범위와 실제 채용 공고를 확보한 범위를 구분하라. 공고의 `Lead`, `Manager`, `팀장`만 보고 인사권을 추정하지 말라.

## 실행 순서

1. **목표와 제출 조건을 확정하라.** 공고 원문·확인일, 필수/우대/업무, 문서 종류, 회사 지정 양식·문항 순서·분량·파일 형식을 읽어라. 사용자가 이미 준 정보로 진행하라. 새로 다루는 직무나 근거가 부족한 직무는 그 직무의 공식 공고·역할 자료를 조사하라. 목표 공고가 없으면 유사 공고로 직무의 책임과 성과 기준을 확인하고 일반 지원 초안임을 밝혀라. 특정 회사 요건을 만들지 말고 검색 요약과 직접 읽은 본문을 구별하라.
2. **지원자의 사실을 대조하라.** 회사·기간·고용형태·공식 직책·실제 역할·직속 인원·프로젝트 인원·권한·개인 행동·팀 산출물·결과·근거를 정리하라. 이번 요청의 명시적 정정을 반영하되 충돌을 숨기거나 유리한 값을 선택하지 말라. 자료가 없는 JD 항목은 내부 확인 목록에 남기고 나머지 작성을 계속하라.
3. **직무와 책임별로 JD에 대응하라.** 직무별 참고표의 조사 절차와 포함·제외 경계로 책임을 분류하고, 핵심 결과 책임을 근거로 대표 기능과 보조 책임을 정하라. 새 직무라는 이유로 미확정 처리하지 말라. 조사로 확인한 책임은 분류하고, 조사 후에도 남는 기업별 책임 차이·권한·대표 기능의 우선순위만 구체적인 확인 사항으로 남겨라. 공고의 독립 책임에서 미배정·다중배정·성과 중복이 없는지 확인하라. 실제 경험·출처를 연결하고 인사관리와 업무 리딩, 수립과 승인, 기획과 구현을 분리하라.
4. **경력과 성과를 검산하라.** 겹친 재직 기간은 합집합으로 계산하라. 연구·계약·시간제 경력의 포함 근거와 채용사의 인정 여부를 분리하라. 기간 JSON이 있으면 `python3 scripts/career_months.py INPUT.json --as-of YYYY-MM`를 실행하라. 월 계산은 정확한 재직 일수나 필수 연수 충족 판정이 아니다. KPI는 전후 값·기간·분모·대상·집계 방법과 개인 기여를 확인하라. 목표 달성은 목표와 실측의 기준시점·조건이 일치할 때만 쓰고 목표를 정한 주체도 확인하라.
5. **경력의 중심과 이유를 드러내라.** 확인된 경력의 출발점→현재 전문성→반복해 해결한 문제를 이어라. 상단 요약과 관련 성과를 먼저, 회사별 경력과 대표 프로젝트를 뒤에 두되 지정 양식은 유지하라. 문제/범위→본인 판단·행동→산출물·확인된 결과를 쓰고, 왜 중요한 문제였는지, 왜 그 방법·순서를 택했는지, 결과가 왜 의미 있는지 독자에게 필요한 연결을 설명하라. 제공 자료에서 판단 기준·제약·목표를 찾아 보존하되 실제로 검토하지 않은 대안·동기·인과를 만들지 말라. 공개 직무 자료를 지원자 개인의 당시 판단 근거로 바꾸지 말라. 지원 동기와 입사 후 계획은 과거 실적과 구별하라.
6. **제출본을 점검하라.** 요약·경력기술서·자기소개서의 기간·직함·역할·수치를 대조하라. 문장 작성에는 사용자가 지정한 한국어 지침을 적용하라. DOCX/PDF가 필요하면 해당 문서 스킬을 사용하고 마지막 수정 뒤 모든 쪽의 렌더·글자 잘림·표·텍스트 추출 순서를 확인하라. 실제 제출 시스템을 시험하지 않고 ATS 통과나 파싱 성공을 주장하지 말라.

## 판단 기준

| 확인한 자료 | 쓸 수 있는 표현 | 추가 근거가 필요한 표현 |
| --- | --- | --- |
| 협력사 포함 프로젝트 인원과 회의 운영 | 참여자 규모, 맡은 조율·우선순위 결정 | 직속 인원 관리, 인사평가·채용 총괄 |
| 정기 1:1 면담의 인원·주기만 확인 | 정기 면담 운영 | 구체적 코칭·피드백 수행, 육성 효과 |
| 요구사항·API·검수 기준 작성, 타 팀 구현 | 본인 설계·검수와 구현 팀의 역할 | 본인이 개발·배포 완료 |
| 회고에서 시간이 줄었다는 의견 | 해당 회고의 정성 피드백, 또는 확인된 산출물 | 측정된 시간 절감률·생산성 개선율 |
| 파일럿 납품·일부 부서 사용 | 파일럿 범위·기간·산출물·관측값 | 전사 정착, 매출 기여, 투자 수익 |
| 부서 간 대기시간을 줄이고 싶은 관점 | 경험에서 얻은 판단과 향후 기여 방향 | 과거에 이미 달성한 전사 개선 |

직접 보고 인원·예산·채용·코칭 성과가 확인되면 약화하지 말고 구체적으로 제시하라. 근거 없는 수치를 빼는 것이 검증된 리더십까지 지우는 이유는 아니다.

## 결과 전달

요청한 이력서·경력기술서 본문이나 파일을 먼저 제공하라. 그 뒤에 중요한 수정 이유, 해결되지 않은 사실 질문, 실제 수행한 검증 범위만 짧게 덧붙여라. JD 대응표·근거 장부는 요청 시 별도 부록으로 전달하라. 제출 문서 안에 작업 지시·`[확인 필요]`·미측정 주석을 반복 삽입하지 말라. 반드시 필요한 사실이 비어 있으면 그 문항은 별도로 알려 해결하고, 문서 전체가 제출 준비를 마쳤다고 말하지 말라.

개인 이력서 원문·연락처·보상정보·사내 자료를 스킬 저장소나 공개 예문에 넣지 말라. 요청받은 문서 저장과 외부 지원·전송은 별개로 처리하라. 공고 사례는 합격 사례가 아니며, 문장 공식·쪽수·ATS 점수·합격률을 보장하지 말라.
