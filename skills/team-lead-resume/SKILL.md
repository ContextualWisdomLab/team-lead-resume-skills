# 팀장급 이력서 작성과 검토

채용 공고에서 요구하는 책임을 지원자가 실제로 맡았던 일과 연결하라. **사람을 관리하고 의사결정을 내리며 사업 결과를 책임진 범위와 근거**를 확인하라. 확인된 성과는 구체적으로 쓰고, 불명확한 사실로 빈칸을 채우지 말라.

## 필요한 자료를 고르기

| 작업 | 읽을 파일 |
| --- | --- |
| 유사 팀장급 채용 조사·한국 테크 기업 사례·직무별 책임 비교 | [채용 사례와 출처](references/hiring-cases.md) |
| 새로 다루는 직무 조사, MECE 기능 분류와 경계, 복합 직무·직무 전환 | [직무별 참고표](references/role-families.md) |
| 공고의 직무 설명(JD)과 경력 대조, 업무를 이끈 범위·성과·경력 연수 판단 | [경력 근거를 정리하는 절차](references/evidence-workflow.md) |
| 한국어 초안·지정 양식·분량·DOCX/PDF 제출 | [작성과 제출](references/writing-and-delivery.md) |

이 스킬은 최종적으로 책임지는 산출물을 기준으로 15개 기능을 구분한다. 한 책임에는 한 기능을 배정하고, 복합 직무는 독립적으로 맡은 책임으로 나누어라. AX·데이터 같은 기술, 산업, 관리 수준은 별도 속성으로 기록하라. 기능 분류가 다루는 범위와 실제 채용 공고를 조사한 범위를 구분하라. 공고의 `Lead`, `Manager`, `팀장`이라는 직함만 보고 인사권을 추정하지 말라.

한국 테크 기업에 지원할 때도 목표 기업의 현재 공고를 우선하라. 회사·시장의 특성은 기능과 별도로 기록하고, 과거 역할 인터뷰와 현재 채용 요건을 구별하라. 한국 테크 기업 비교표에서 사례별 책임·권한과 경력을 확인할 질문을 고르라.

## 실행 순서

1. **목표와 제출 조건을 확정하라.** 공고 원문과 확인일, 필수 요건·우대 요건·담당 업무를 확인하라. 문서 종류와 회사 지정 양식, 문항 순서·분량·파일 형식도 살펴라. 사용자가 이미 준 정보로 진행하라. 새로 다루는 직무나 근거가 부족한 직무는 해당 직무의 공식 공고와 역할 자료를 조사하라. 목표 공고가 없으면 유사 공고에서 책임과 성과 기준을 확인하고, 일반 지원을 위한 초안임을 밝혀라. 회사별 요건을 만들어 넣지 말고, 검색 요약과 직접 읽은 본문을 구별하라.
2. **지원자의 경력 사실을 대조하라.** 회사·기간·고용 형태·공식 직책·실제 역할을 정리하라. 직속 인원과 프로젝트 참여 인원, 권한, 개인 행동과 팀의 산출물·결과를 근거와 연결하라. 사용자가 이번 요청에서 명시적으로 바로잡은 사실을 반영하되, 자료 간 충돌을 숨기거나 유리한 값을 고르지 말라. 근거가 없는 JD 항목은 내부 확인 목록에 남기고 나머지 작성을 계속하라.
3. **직무와 책임별로 JD에 대응하라.** 직무별 참고표의 조사 절차와 포함·제외 기준에 따라 책임을 분류하라. 핵심 결과를 책임지는 기능을 중심으로 대표 기능과 보조 책임을 정하라. 새 직무라는 이유로 분류를 미루지 말라. 조사로 확인한 책임부터 분류하고, 기업별 책임 차이·권한·대표 기능의 우선순위처럼 조사 후에도 남는 사항만 구체적인 확인 질문으로 남겨라. 각 독립 책임에 기능이 빠짐없이 하나씩 배정됐는지, 같은 성과를 중복 계산하지 않았는지 확인하라. 실제 경험과 출처를 연결하고, 인사관리와 업무를 이끈 경험, 수립과 승인, 기획과 구현을 구분하라.
4. **경력과 성과를 검산하라.** 재직 기간이 겹치면 합집합으로 계산해 중복을 제외하라. 연구·계약·시간제 경력을 계산에 포함한 근거와 채용사가 그 경력을 인정하는지는 구분하라. 기간을 담은 JSON이 있으면 `python3 scripts/career_months.py INPUT.json --as-of YYYY-MM`를 실행하라. 월 단위 계산만으로 정확한 재직 일수나 필수 경력 연수의 충족 여부를 판단하지 말라. 성과 지표(KPI)의 전후 값·기간·분모·대상·집계 방법과 개인 기여를 확인하라. 목표를 정한 주체를 확인하고, 목표와 실측값의 기준 시점·조건이 일치할 때만 목표 달성을 서술하라.
5. **경력의 중심과 판단 이유를 드러내라.** 외부 독자가 모를 내부 명칭·약어·전문 개념은 [작성과 제출](references/writing-and-delivery.md)에 따라 공개 공식 자료나 승인된 근거를 조사해 목적·기능을 설명하라. 독자의 배경을 고려하고 비공개 표현을 외부 검색에 보내지 말라. 확인된 경력의 출발점, 현재의 전문성, 반복해 해결한 문제를 이어라. 상단 요약과 관련 성과를 먼저, 회사별 경력과 대표 프로젝트를 뒤에 두되 지정 양식은 유지하라. 문제와 범위, 본인의 판단·행동, 산출물과 확인된 결과를 연결하라. 왜 중요한 문제였는지, 왜 그 방법·순서를 택했는지, 결과가 왜 의미 있는지 독자가 이해하는 데 필요한 이유를 설명하라. 제공 자료의 판단 기준·제약·목표를 보존하고, 실제로 검토하지 않은 대안이나 확인되지 않은 동기·인과관계를 만들지 말라. 공개 직무 자료를 지원자 개인의 당시 판단 근거로 바꾸지 말라. 지원 동기와 입사 후 계획은 과거 실적과 구별하라. 사용자가 포부·기여 방향을 요구하거나 지원 문항이 이를 묻는 경우, [작성과 제출](references/writing-and-delivery.md)의 문서별 배치 기준에 따라 **확인된 경험 → 지원 직무의 과제 → 앞으로 맡을 행동**을 연결하라. 세 문서를 함께 요청받았다면 각 문서의 역할에 맞게 반영하라.
6. **제출본을 점검하라.** 요약·경력기술서·자기소개서의 기간·직함·역할·수치를 대조하라. 요청받은 기여 방향이 해당 문서에서 빠지지 않았는지, 과거 성과와 미래의 행동이 구별되는지도 확인하라. 한국어를 쓰거나 편집할 때는 [작성과 제출](references/writing-and-delivery.md)에 연결된 `korean-editing` 지침을 읽고 적용하라. DOCX/PDF가 필요하면 해당 문서 스킬을 사용하라. 마지막 수정 뒤 모든 쪽을 렌더링해 글자 잘림과 표를 확인하고, 텍스트 추출 순서도 점검하라. 실제 제출 시스템을 시험하지 않고 ATS 통과나 정보 추출 성공을 주장하지 말라.

## 판단 기준

| 확인한 자료 | 쓸 수 있는 표현 | 추가 근거가 필요한 표현 |
| --- | --- | --- |
| 협력사를 포함한 프로젝트 인원과 회의 운영 기록 | 참여자 규모, 본인이 맡은 조율·우선순위 결정 | 직속 인원 관리, 인사평가·채용 총괄 |
| 정기 1:1 면담의 인원·주기만 확인 | 정기 면담 운영 | 구체적 코칭·피드백 수행, 육성 효과 |
| 본인이 요구사항·API·검수 기준을 작성하고 다른 팀이 구현함 | 본인의 설계·검수와 구현 팀의 역할 | 본인이 개발·배포를 완료했다는 주장 |
| 회고에서 시간이 줄었다는 의견 | 해당 회고의 정성 피드백, 또는 확인된 산출물 | 측정된 시간 절감률·생산성 개선율 |
| 파일럿 납품·일부 부서 사용 | 파일럿 범위·기간·산출물·관측값 | 전사 정착, 매출 기여, 투자 수익 |
| 부서 간 대기 시간을 줄이고 싶다는 관점 | 경험에서 얻은 판단과 앞으로 기여하려는 방향 | 과거에 이미 달성한 전사 개선 성과 |

직속 인원, 담당 예산, 채용·코칭 성과가 확인되면 구체적으로 제시하라. 근거 없는 수치를 빼면서도 검증된 리더십과 성과는 분명히 남겨라.

## 결과 전달

요청한 이력서·경력기술서 본문이나 파일을 먼저 제공하라. 그 뒤에 중요한 수정 이유, 아직 확인할 사실, 실제로 수행한 검증의 범위를 짧게 덧붙여라. JD 대응표와 근거 목록은 요청받았을 때 별도 부록으로 전달하라. 제출 문서 안에 작업 지시나 `[확인 필요]`, 측정하지 않았다는 주석을 반복해서 넣지 말라. 필수 사실이 비어 있으면 해당 문항과 필요한 자료를 별도로 알리고, 문서 전체가 제출 준비를 마쳤다고 말하지 말라.

개인 이력서 원문·연락처·보상정보·사내 자료를 스킬 저장소나 공개 예문에 넣지 말라. 요청받은 문서 저장과 외부 지원·전송은 별개로 처리하라. 공고 사례는 합격 사례가 아니며, 문장 공식·쪽수·ATS 점수·합격률을 보장하지 말라.
