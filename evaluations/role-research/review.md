# 직무 조사와 판단 이유 보강 검증

## 요청과 변경

새 직무라는 이유로 미확정 처리하지 않고 그 직무를 조사하며, 독자가 갖는 ‘왜?’에 답하도록 0.3.0을 수정했다. 기존의 15개 기능과 기간 계산기는 유지했다. 새 이름 자체가 근거 부재는 아니라는 판단, 공개 직무 맥락과 지원자의 당시 판단을 구분하는 기준을 핵심 절차에 반영했다.

## 적용 설계와 판본

- [입력](input.md)은 실제 개인·사내 정보를 쓰지 않은 RevOps 지원 과제다. 이유·비교 대안·운영 기준이 있는 경험과 이유가 제공되지 않은 경험을 함께 두었다.
- [12개 기준](criteria.md)을 실행 전에 작성했고 실행자는 읽지 않았다. 이력서 본문은 전문성 요약 2문장과 프로젝트 2항목, 900자 이내다.
- [기준 판본](baseline-version.json)은 공개 `fb1ac438caac19ffe2828dd6421a25410e46e793`의 0.2.0이다. [수정 후보](application-version.json)는 설치 경로에서 먼저 수정한 0.3.0이다. 파일·입력·기준 해시는 실행 전에 기록했다.
- 두 실행 모두 새 문맥에서 지정한 스킬과 입력만 제공받고 외부 조사를 허용했다. 기대 답안·진단·다른 실행 결과는 전달하지 않았다. 실행이 길어져 부모가 중단한 뒤 같은 문맥에서 이미 읽은 자료로 마무리하도록 했다. 두 실행의 중단 시점과 사용한 출처가 같지 않아 시간·도구 성능의 통제 비교는 아니다.
- 배포 예제는 FDE·행사 접수이고 적용 입력은 RevOps·갱신 정보 운영이다. 다만 스킬 수정자와 입력·기준 작성자가 같으므로 완전히 독립적인 평가 설계는 아니다.

### 발견 후 보완과 재적용

1. 독립 검토는 스킬 본문·역할표·증거 절차·작성 지침 전체와 채용 사례 H16까지를 읽었다. 합성 예문이 우선순위 결정자를 밝히지 않은 채 지원자의 선택처럼 서술한 문제를 찾았다. 예문을 결정에 따라 수행한 행동으로 고쳤다. 검토자가 H17 이후나 전체 diff까지 확인한 것으로 기록하지 않는다. H17–H20 원문과 전체 변경은 부모가 별도로 확인했다.
2. 첫 적용에서 드러난 목표 설정 주체와 측정 기준시점 문제를 공통 지침으로 보완했다. 합의한 목표를 본인이 정한 것으로 쓰지 않고, 목표의 대상·분모·기준시점·집계 조건이 실측과 맞을 때만 달성을 쓴다. 설명 예제는 갱신 입력과 다른 주문 확인율을 사용했다.
3. 같은 실행자에게 현재 지침과 원자료를 다시 읽고 본문·질문만 작성하도록 했다. 구체적 오류나 기대 문장은 전달하지 않았다. 재적용에서는 기준을 ‘합의됐습니다’로 표현하고 목표 달성을 단정하지 않았으며, 45일 전 상태를 기준으로 측정했는지와 두 번째 경험의 선택 이유를 질문했다. 문제·일정·대안·제안·승인·구현·관측 조건도 보존했다.

재적용은 앞선 문맥을 가진 실행자의 수정 확인이다. 새로운 독립 과제의 성공이나 일반화 성능으로 해석하지 않는다. 실행 이후의 수정은 [패치](post-application-edits.patch)에 남겼으며 이를 역적용하면 첫 적용의 해시를 재구성할 수 있다. 세 긴 참고 파일의 목차 추가도 이 패치에 포함된다.

### 직무 조사 도구의 확인 범위

수정 후보의 일반 웹 열람은 Primer에서 JavaScript 안내, Firecrawl에서 404를 반환했다. 실행자는 이후 TinyFish `fetch_content`의 공식 URL 추출 응답에 본문이 반환되어 읽었다고 보고했다. 최종 비교는 그 본문을 사용했으며 검색 발췌와 상충한 Firecrawl 설명도 추출 본문을 따랐다. 부모의 일반 웹 재열람에서도 JS 안내·404가 나왔고 TinyFish 추출을 독립적으로 다시 실행하지는 않았다. 따라서 이를 일반 웹 도구로 본문 열람 성공, HTTP 200 확인, 현재 모집 중으로 기록하지 않는다. 실행 경로와 읽은 파일은 판본 JSON에 보존한다. 이 두 RevOps 공고는 배포 장부의 직접 검증한 H1–H20에 추가하지 않았다.

## 자료 조사 확인

H13–H20의 고용주 공식 상세 본문을 확인했다. FDE 두 기업 사례 외에 생산·고객지원·시설·EHS·준법·대외관계 전담 공고를 확보했다. 15개 기능 모두에 실제 책임의 사례가 연결되지만 모든 하위 직무·산업의 공통 채용 요건을 입증하지는 않는다.

검토 중 Bosch 시설관리 공고는 조사자의 색인 본문 열람 뒤 최종 확인에서 만료 화면만 보였다. 현재 본문 열람 가능한 사례로 기록하지 않고 H17의 Amazon 공식 공고로 교체했다. 공고의 지원 링크·양식이 보이는 것과 실제 접수 가능·채용 완료는 구분했다. 새 공고의 원문·확인일·게시/마감 표시·권한의 한계는 배포용 출처 장부에 기록했다.

## 형식과 계산 확인

- 설치 경로에서 제작 도구의 `quick_validate.py` 실행: `Skill is valid!`.
- 같은 설치 경로를 `TEAM_LEAD_SKILL_DIR`로 지정해 기존 계산기 unittest 9개 실행: 모두 통과. 계산기 코드는 변경하지 않았다.
- 로컬 Markdown 참조 대상 확인, H1–H20 번호 연속성, 15기능의 실제 사례 참조 연결 확인.
- 보완한 최종 설치 파일에서 형식 검사를 다시 통과했다. 계산기 파일은 최초 9개 테스트를 통과한 파일과 동일하다. 적용 응답의 원문은 수정하지 않고 각 판본 JSON에 해시를 기록했다.

## 관찰 한계

합성 과제의 단일 적용이며 실제 지원자·채용 결과·ATS 시스템을 검증하지 않았다. 이전 0.2.0 E16·E18은 외부 조사를 금지한 입력의 관찰이다. 이를 현재 조사 기본 동작의 성공·실패 증거로 재사용하지 않는다. 사용 가능한 공식 자료와 모델의 판단이 달라지면 결과도 달라질 수 있다.

## 설치와 배포 파일

최종 개인 스킬의 활성 경로와 원격 저장 파일 8개(플랫폼 메타데이터·아이콘 포함)의 바이트를 대조했다. 공개 배포 단위는 기존 7파일이며 본문·참조·계산기는 설치본과 동일하고 UI 메타데이터의 작성 필드도 일치한다. 플랫폼 전용 아이콘·제품 표시는 공개 배포본에 덧붙이지 않았다. 최종 배포 해시는 루트 `manifest.json`에 기록했다. 개인 스킬의 최종 변경 커밋은 `8de4980`이다.
